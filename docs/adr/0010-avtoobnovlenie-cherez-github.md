# 0010. Автообновление через публичный GitHub с самопересборкой

## Контекст

Пользователь попросил автоматическое обновление приложения при появлении новых
версий (G11, тикет 13). Ограничения проекта: нет Apple Developer ID (подпись
только ad-hoc), нет внешних зависимостей, сборка ведётся на Linux-сервере, а
единственная macOS-машина — Mac пользователя. Значит, готовый подписанный бинарь
доставить нечем: любой скачанный .app с ad-hoc подписью всё равно упрётся в
Gatekeeper и потерю TCC-доверия. Зато на Mac пользователя уже есть Xcode CLT и
проверенный `build.sh` — приложение изначально ставится сборкой из исходников.

## Решение

Канал обновления — публичный GitHub-репозиторий `alimp01/mac-layout-switcher`
(репо переведено в public именно ради этого):

- **Проверка версии** — GET `raw.githubusercontent.com/.../main/VERSION`
  (одна строка semver), раз в сутки и по пункту меню «Проверить обновления…».
- **Режим «уведомить + обновить по клику»**: при новой версии — алерт с обеими
  версиями; «Позже» ничего не делает, молча приложение не обновляется.
- **Самопересборка из исходников** на Mac пользователя (`tools/self-update.sh`,
  запускается detached): скачать `main.tar.gz`, собрать `build.sh` во временной
  папке, только после успешной сборки атомарно заменить .app на прежнем пути,
  перезапустить. При любом сбое существующий .app не трогается, всё в лог
  `~/Library/Logs/MacLayoutSwitcher-update.log`.

## Почему

Пересборка из исходников — единственный способ доставки, который уже доказанно
работает в этом проекте (так приложение и устанавливается), не требует ни
Developer ID, ни инфраструктуры релизов, ни зависимостей. Публичный GitHub даёт
надёжный анонимный канал без токенов в приложении.

Отвергнутые варианты:

- **Sparkle-фреймворк** — внешняя зависимость, а проект принципиально без
  зависимостей; вдобавок Sparkle рассчитан на подписанные бинарные релизы,
  которых у нас нет.
- **Бинарные релизы GitHub Releases** — без Developer ID подпись остаётся
  ad-hoc: Gatekeeper и TCC-разрешения сбрасываются точно так же, как при
  пересборке, а публикация бинаря добавила бы отдельный релизный процесс
  (сборку на Mac, выкладку артефактов) без выигрыша.
- **Полностью молчаливое автообновление** — внезапный перезапуск посреди работы;
  отвергнуто пользователем в пользу «уведомить + обновить по клику».
- **Канал через приватный репо или архив на своём сервере** — приватный репо
  потребовал бы зашить токен в приложение (нельзя), а свой сервер — единая
  точка отказа; GitHub надёжнее.

## Последствия

- Репозиторий публичный — код открыт всем; это осознанная плата за канал.
- После обновления TCC-разрешения (Accessibility + Input Monitoring) выдаются
  заново: заменённый .app с новой ad-hoc подписью теряет доверие. Алерт
  обновления и README честно предупреждают об этом; срабатывает штатный
  онбординг разрешений.
- Обновление занимает ~1–2 минуты (скачивание + сборка) и требует Xcode CLT на
  Mac — то же условие, что и первичная установка.
- Появляются `VERSION` (источник истины версии, build.sh подставляет её в
  Info.plist), `SemVer.compare` в тестируемом ядре и `tools/self-update.sh` в
  бандле; изменение версии = правка одной строки в `VERSION` на main.
- Обновление привязано к ветке `main`: что в main — то и «релиз», отдельного
  канала стабильности нет.

# 0001. SwiftPM без Xcode-проекта, ядро тестируется на Linux

## Контекст

У агента, который пишет и проверяет код, нет macOS-машины — только Linux-сервер.
Пользователь собирает готовый `.app` сам на своём Mac и хочет делать это одной
командой.

## Решение

Проект — чистый пакет SwiftPM без `.xcodeproj`. Ядро (`SwitcherCore`: детектор,
конвертер, буфер слова, шаблоны) не зависит от системных API и компилируется под
Linux; весь системный слой (`app.*`: event tap, TIS, синтетический ввод, меню-бар)
закрыт `#if os(macOS)`. `swift test` гоняет ядро на Linux в CI; `./build.sh`
собирает `.app` на Mac пользователя.

## Почему

Тестируемость ядра там, где живёт агент, — главный критерий. Рассмотрели и отвергли:

- **Xcode-проект (.xcodeproj/.xcworkspace).** Не собирается и не тестируется без
  macOS и без установленного Xcode — агент не смог бы прогнать ни одного теста до
  сдачи. Плюс `.pbxproj` правится только внутри Xcode либо хрупкими скриптами, что
  несовместимо с автоматической сборкой в этой среде.
- **Единый монолитный target macOS-приложения.** Тогда даже чистая логика
  детектора тянет за собой AppKit/HIToolbox и не компилируется на Linux — 0 тестов
  до сборки на Mac.

## Последствия

- Весь `app.*` слой не покрыт автотестами у агента; корректность event tap, TIS и
  синтетического ввода подтверждается только приёмкой на Mac пользователя по
  чек-листу README (R07i). Регрессии в системном слое агент не увидит.
- Разделение «ядро / `#if os(macOS)`» приходится держать дисциплинированно: любой
  системный вызов, просочившийся в `SwitcherCore`, ломает сборку на Linux.
- Нет благ Xcode из коробки — нет GUI-отладчика Instruments, управление ресурсами и
  Info.plist для `.app` собирается вручную в `build.sh`.
